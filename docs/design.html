Codex Micro pane 대시보드

Codex Micro 매크로패드를 iTerm2 병렬 Claude Code 워크플로우의 상태 표시기 겸 제어 장치로 쓴다. 6개 Agent 키가 현재 탭의 pane별 상태를 색으로 보여주고, 누르면 그 pane으로 이동한다.

01 배경과 요구사항

기존 OSS FreeMicro를 설치해 써봤으나 같은 디렉터리의 세션을 키 하나로 합쳐버려 한 repo에서 pane 4~6개를 병렬로 돌리는 방식과 맞지 않았다. 그 외 설치 부담과 Codex 앱과의 LED 경합도 있었다.

#요구
R1각 pane의 Claude Code 상태를 키별 색으로 표시
R2키를 눌러 해당 pane으로 전환

6키에 한정한다. 테두리는 계속 쓴다(05), 완전한 격리는 불가능하다(03)
R5테두리 LED도 상태 표현에 활용, 표시 내용은 설정 가능
R6패드 락 충돌이 없을 것 — 패드를 두고 다투는 우리 프로세스는 하나뿐.

R7탭 전환은 직접 주소 지정과 순차 순환을 모두 제공하고 각각 끌 수 있을 것
R6의 정직한 범위

FreeMicro를 걷어낸 사유는 넷이었는데(pane 개별 처리 불가, 설치 부담, TCC 권한, 락 충돌), 이 설계는 상주 데몬을 그대로 요구한다. 그건 피할 수 없다.

실제로 줄어드는 것:

  • TCC 권한 불필요 — 2026-07-26 정정. 초안은 Input Monitoring이 필수라고 적었으나 실측에서 뒤집혔다. VID/PID로 이 기기만 매칭해 IOServiceGetMatchingServices로 열면 권한 없이 읽고 쓴다. 권한이 필요했던 것은 모든 HID 기기를 매칭해 열던 방식이었다 (하드웨어 노트)
  • 패드 락 충돌 없음 — 웹 편집기·데몬·CLI가 서로 패드를 뺏던 구조가 없다. 프로세스는 데몬 하나
  • 훅 미설치 세션도 보인다 — jobName으로 pane을 찾으므로(06), 훅 설치 후 재시작 전까지 통째로 안 보이는 문제가 없다
  • Accessibility 권한 불필요 — 키를 합성하지 않고 iTerm2 API로 pane을 고른다

“설치가 가벼워진다”는 여전히 주장하지 않는다 — 데몬은 남는다.

02 전제 — 하드웨어

설계가 딛고 선 실측 사실. 근거와 측정 방법은 하드웨어 노트에 있다.

기능Layer 1Layer 2+
A키·C키·노브 → 벤더 이벤트있음없음
키 → 표준 스캔코드없음있음
A1~A6 개별 색 (thstatus)가능무시됨
C키 백라이트 / 테두리 (rgbcfg)가능가능

Layer 1만이 R1(개별 색)과 R2(입력)를 동시에 만족한다. 따라서 무대는 Layer 1이고, Layer 2+는 사용자 커스텀 영역으로 남긴다.

여기서 파생되는 제약 셋:

  • LED는 읽을 수 없다 — 누가 덮어썼는지 감지할 방법이 없다
  • 디바이스가 non-exclusive로 열린다 — 벤더 앱의 이벤트 수신을 막을 수 없다
  • 성공 리턴 코드는 무의미하다 — device.status 왕복만이 검증 수단

03 소유권 — 두 게이트

레이어 게이트가 “동작할지”를, frontmost 게이트가 “무엇을 소유할지”를 정한다.

레이어 게이트

layer_index != 1이면 6키(thstatus)와 입력을 모두 포기한다. 다만 테두리는 Layer 2+에서도 하드웨어가 지원하므로 설정으로 유지할 수 있다. 

"layer_gate": { "keys": "off", "underglow": "keep" }   // underglow: keep | off
레이어로 “끄기”를 하지 말 것

터치 센서는 순환이라 Layer 2로 나갔다 돌아오려면 최대 5탭이고, 그 과정에서 사용자가 설정해둔 커스텀 레이어가 차례로 활성화된다. 잠깐 끄려던 동작이 키맵을 훑고 지나간다.

끄기는 gate.mode: "off"(소프트웨어)로 한다. 레이어 순환은 커스텀 용도로 남긴다.

frontmost 게이트 — 존별로 소유권이 다르다

“침묵한다”가 아니라 어느 존을 양보하는지를 존 단위로 정한다. 이렇게 해야 R4(6키 양보)와 R5(테두리 활용)가 충돌하지 않는다.

보고 있는 앱6키 테두리A키 입력
ChatGPT벤더에게 양보우리가 유지처리 안 함
iTerm2우리우리처리
그 외직전 소유권 유지 — 직전이 iTerm2였으면 그 탭까지 유지하고 입력도 처리한다. 직전이 ChatGPT였으면 입력을 처리하지 않는다
기동 직후관심 앱이 처음 frontmost가 될 때까지 무소유 — 6키 소등, 입력 처리 안 함

감지는 NSWorkspace 활성 앱 변경 알림으로 한다(폴링 폴백 1초). 식별자는 표시 이름이 아니라 bundle identifier다 — 표시 이름은 언어·버전에 따라 바뀐다. 이 경로는 TCC 권한이 필요 없다.

양보할 때는 6키를 끄고 넘긴다

벤더가 언제 다시 그리는지 알 수 없으므로, 그냥 손을 떼면 우리 pane 색이 그대로 남아 사용자가 Codex 스레드 상태로 오독한다. 양보 시점에 6키를 명시적으로 소등한 뒤 넘긴다.

막을 수 없는 것

디바이스가 non-exclusive라 iTerm2를 보면서 A키를 눌러도 ChatGPT 앱이 백그라운드에서 자기 스레드를 바꾼다. 상대 프로세스의 수신을 막을 수단이 없다. (벤더 동작이 백그라운드 선택이라 창은 안 뜨는 것으로 보이나 미검증 — 12)

반대 방향은 깨끗하다 — Codex를 볼 때 우리는 6키를 건드리지 않는다. R4는 이 방향에만 적용된다.

LED 경합 — 완화이지 해결이 아니다

LED를 읽을 수 없으니 덮어쓰기를 감지할 수 없다. 주기적 재도색은 last-writer 경쟁이라 깜빡임과 채널 경쟁을 부르므로 하지 않는다. 이름 붙일 수 있는 사건에서만 다시 칠한다 — 게이트 전환, 레이어 변화, 패드 재연결, 절전 복귀, pane 구성 변경. 그 사이 벤더가 덮어쓴 색은 다음 사건까지 남는다.

같은 6개 LED로 두 계층을 표현한다. MOD+A3은 언제나 탭 3이라 순환이 아닌 직접 주소 지정이고, 근육 기억이 생긴다.

MOD 키

기본 C7. C5·C6은 넓은 캡 하나를 공유해 두 id가 함께 발생하므로 후보에서 제외한다. KNOB_PRESS도 가능하다.

MOD 고착을 막는다

MOD를 누른 채 레이어를 바꾸거나 앱을 전환하면 release가 오지 않는다 — Layer 2+에는 벤더 이벤트가 아예 없고, 게이트가 닫히면 입력을 버리기 때문이다. 그대로 두면 Layer 1으로 돌아왔을 때 A키가 전부 탭 전환으로 동작하고 사용자는 이유를 알 수 없다.

  • 게이트 전환·레이어 변화 시 MOD 상태를 무조건 리셋
  • press 후 5초간 이벤트가 없으면 자동 해제

노브는 회전이 act=2로 오고 press/release 쌍이 없다. 키와 같은 act==1 필터를 걸면 다이얼이 통째로 죽는다.

승인·거절 — 대상은 “지금 보고 있는 pane”

승인은 되돌릴 수 없는 유일한 동작이므로 대상을 찾지 않는다. 이미 포커스된 pane에만 보낸다.

위를 모두 통과그 pane에 답을 보낸다

쓰는 흐름은 “A키로 간다 → 화면으로 내용을 본다 → C2✓”다. 사람이 직접 보고 있는 것이 곧 확인 절차이므로 별도 확인 단계가 없다. 대상 선택 규칙도, 화면 밖 pane에 승인이 나갈 위험도 존재하지 않게 된다.

보내는 내용은 Claude Code 권한 프롬프트의 응답 키다. 구체적인 키 전송 방식은 미검증이며 구현 전 확인한다(12).

05 테두리

규칙은 하나 — 지금 6키에 안 보이는 것 중 나를 기다리는 것을 알린다.

보고 있는 곳집계 대상
iTerm2다른 탭들 + 현재 탭에서 6키에 못 올라간 pane
Codex모든 Claude Code — 전부 화면 밖이므로
그 외직전 소유권 기준

집계 결과가 waiting이면 주황, error면 빨강, 그 외에는 끈다. 둘 다 있으면 탭 뷰와 같은 우선순위(waiting > error > done > working > idle)를 따른다. done·working·idle을 끄는 이유는 켜두면 테두리가 항상 켜져 신호가 죽기 때문이다.

7번째 pane이 사라지지 않게

집계 대상에 “현재 탭에서 6키에 못 올라간 pane”을 포함하는 것이 핵심이다. 단순히 “다른 탭들”로 정의하면 현재 탭의 7번째 pane이 6키에도 테두리에도 없어 완전히 사라진다 — 안전망이 하필 그 케이스에서만 작동하지 않는다.

테두리는 탭 뷰로 가는 신호이기도 하다 — 주황이 뜨면 MOD로 어느 탭인지 확인하고 MOD+An으로 건너간다.

06 상태 — 훅과 저장

pane 발견은 iTerm2, 상태는 훅

Claude Code가 떠 있는 pane인지는 iTerm2의 jobName으로 안다 (버전 문자열 형태로 나온다). 훅은 상태에만 필요하다.

덕분에 훅이 아직 안 붙은 세션도 “Claude Code는 있으나 상태 미상”으로 표시할 수 있다. 다만 이 판별은 버전 문자열 표기에 의존하므로 Claude Code 업데이트로 깨질 수 있다 — 깨지면 그 pane은 “Claude Code 없음”으로 보이고, 훅이 붙어 있으면 상태로 보정된다.

세션 생존 판정

TTL만으로는 “오래 대기 중”과 “종료됨”을 구분할 수 없다. 훅은 상태가 바뀔 때만 오므로 30분째 승인을 기다리는 세션과 죽은 세션이 똑같이 조용하다.

  • iTerm2에 그 tty가 없으면 죽은 것 — 있으면 아무리 조용해도 살아 있다
  • 같은 tty에 레코드가 둘 이상이면 updated_at 최신만 채택하고 나머지는 즉시 삭제. 한 pane에서 Claude Code를 껐다 켜면 실제로 생기며, 옛 레코드가 waiting이면 죽은 세션으로 승인을 보내려 할 수 있다
  • TTL(기본 30분)은 iTerm2 조회가 실패할 때의 안전망일 뿐이다

07 세대와 입력 안전

보이는 것과 눌렀을 때 가는 곳이 어긋나지 않게 묶는다.

LED 갱신이 실패했는데 입력을 계속 받으면 화면은 옛 배치인데 키는 새 배치로 라우팅된다. 잘못된 pane으로 가고, 그 위에 승인 키가 올라간다. 

generation N = { panes[], colors[], layer, owner }

  LED 쓰기 성공 + device.status 왕복 성공  →  세대 N 확정, 입력은 N 의 panes[] 로
  둘 중 하나라도 실패                      →  세대 N 폐기, 입력 잠금 (fail-closed)

입력이 잠긴 동안 A키를 눌러도 아무 일도 없다. 엉뚱한 pane으로 가느니 아무 데도 안 가는 편이 낫다.

pane 구성이 바뀌면(split 생성·종료) 새 세대로 교체하며, 교체가 끝날 때까지 입력을 잠근다. 여러 A키의 대상이 한꺼번에 이동하는 순간이므로 짧더라도 반드시 잠근다.

목표 지연

경로목표
상태 변화 → LED 반영500ms 이내
A키 press → pane 이동150ms 이내
데몬 상태 폴링250ms
frontmost 감지알림 기반(폴백 1초)

pane 15개 병렬에서 훅 호출이 몰릴 때 이 목표를 지키는지는 미검증이다. 못 지키면 폴링 간격을 늘리고 LED 갱신을 합친다.

09 경계 조건과 실패

전부 fail-closed. 엉뚱한 곳에 보내느니 아무것도 하지 않는다.

상황동작
layer_index != 16키·입력 포기. 테두리는 설정에 따라 유지
게이트가 벤더 소유6키 소등 후 양보, 입력 처리 안 함
pane 6개 미만남는 키 소등
pane 7개 이상앞 6개를 6키에. 나머지는 테두리 집계에 포함
탭 7개 이상탭 뷰는 6개까지. 초과분은 노브로만 도달 — 노브를 끄면 도달 불가하므로 설정 시 경고
iTerm2 창 여러 개가장 최근 활성 창 1개만 다룬다. 다른 창은 집계에서 제외
Claude Code 없는 pane소등. 키를 누르면 이동은 됨
tty를 못 알아냄아무것도 안 함
패드 미연결재시도. 상태 수집은 계속. 재연결 시 전체 재도색
thstatus 실패세대 폐기 → 입력도 잠금
iTerm2 미실행키 no-op. 앱을 실행시키지 않는다
iTerm2 재시작 / API 끊김매핑 전부 폐기 후 재구축. tty 재사용에 옛 상태를 붙이지 않는다
macOS 절전 → 복귀HID·API·타이머 재수립, 전체 재도색, 경과 시간만큼 TTL 재계산
레이어가 도중에 바뀜쓰기 직전 재확인(TOCTOU). 어긋나면 그 프레임 폐기
데몬 종료6키·테두리를 끄고 나간다 — 낡은 색이 굳어 사용자가 오독하지 않도록

“왜 안 켜지지?”에 답할 수단

키가 어두운 이유는 여럿인데 눈에는 전부 똑같이 보인다. 로그를 열어보게 하는 것은 답이 아니다.

수단알려주는 것
paneglow status 데몬 생존, 권한 상태, 패드 연결·전송, 현재 레이어, 소유권, 세대, 각 키의 배정과 왜 어두운지
paneglow doctor 설치 점검 — 패드 왕복, iTerm2 Python API 활성화, 훅 설치
장애 표시 데몬은 살아 있으나 정상 동작 못 할 때 테두리 느린 깜빡임 — “꺼짐”과 “고장”을 구분

버전 호환성

하드웨어 사실은 모두 firmware v0.4.1에서 나왔다. 기동 시 device.status로 버전을 읽어 다르면 경고하고 계속 진행한다(거부하지 않는다). iterm2 패키지와 Claude Code 훅 스키마도 최소 버전을 기록하고, 어긋나면 doctor가 알린다.

10 설정

~/.paneglow/config.json — 전체 스키마와 기본값. 전부 선택이며 없으면 기본값을 쓴다.

{
  "gate": {
    "mode":      "frontmost",                // frontmost | always | off
    "yield_to":  ["com.openai.chat"],        // bundle id
    "own_when":  ["com.googlecode.iterm2"],
    "otherwise": "keep"
  },
  "layer_gate": { "keys": "off", "underglow": "keep" },

  "mod_key": "C7",                          // C1~C4, C7, KNOB_PRESS  (C5·C6 불가)
  "tab_switch": { "knob": true, "mod_direct": true },   // R7 — 각각 끌 수 있다
  "double_tap": { "enabled": true, "window_ms": 300 },

  "approve": { "enabled": true },           // C2/C3

  "underglow": {
    "when_iterm": { "mode": "outside"    },
    "when_codex": { "mode": "all_claude" },
    "when_other": { "mode": "keep"       },  // keep 은 여기서만
    "colors": { "waiting": "#FF6D00", "error": "#FF0033", "quiet": "off" }
  },

  "state": { "ttl_minutes": 30, "done_fade_seconds": 180 },
  "timing": { "poll_ms": 250, "mod_release_timeout_ms": 5000 },

  "experimental": { "codex_status": { "enabled": false, "source": "ipc" } }
}
키비고
gate.mode frontmost 게이트 사용 · always 항상 우리 소유(ChatGPT 앱을 꺼야 함) · off는 paneglow 전체 비활성(패드를 건드리지 않음)
state.done_fade_seconds 우리 설계 결정이다 — 공장의 “읽지 않음” 의미를 참고했을 뿐 하드웨어 동작이 아니다
설정 오류 해당 키만 기본값으로 폴백하고 doctor에 경고를 남긴다. 기동을 거부하지 않는다
